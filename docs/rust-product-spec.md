# Lazarr на Rust: спецификация нового продукта

Статус: проект требований для обсуждения и последующей разработки.
Дата: 8 октября 2026 года.

## 1. Назначение документа

Это спецификация разработки Lazarr с нуля, а не план перевода существующего кода на Rust. Она определяет, что должен делать продукт, какие решения должен объяснять пользователю и при каких условиях реализацию можно считать готовой.

Существующие классы, таблицы, HTTP-маршруты, очереди, алгоритмы, коэффициенты оценки, SDK и интерфейс не являются ограничениями. Совместимость с ними не требуется по умолчанию. Rust — заданный язык серверного приложения; способ реализации WebUI и допустимость внешних исполняемых компонентов рассматриваются отдельно.

Исходное назначение продукта взято из пользовательской документации Lazarr: управление поиском, получением, проверкой и организацией фильмов, сериалов и аниме; воспроизведение обеспечивает отдельный медиасервер. Исходный код для составления документа не исследовался. Все описанные ниже решения — требования и предложения к новому продукту, а не утверждения о возможностях текущей версии.

Обозначения приоритета:

- **P0** — требуется для первой пригодной к ежедневному использованию версии.
- **P1** — требуется для полного целевого продукта; может поставляться после первой версии.
- **P2** — возможное развитие за пределами этой спецификации.

Если приоритет не указан, применяется P0. Открытые вопросы собраны в разделе 25. До их решения документ задаёт рабочие допущения, а не согласованный окончательный контракт.

## 2. Цель и границы продукта

Пользователь указывает произведение, нужные фильмы или эпизоды и требования к качеству. Lazarr находит подходящие источники, объясняет выбор, получает нужные файлы, проверяет результат и публикует упорядоченную медиатеку. Для продолжающихся сериалов эта работа повторяется по мере выхода новых серий.

Главный результат — корректное и проверенное медиа в библиотеке. Найденная раздача, завершившийся сетевой запрос или скачанный файл сами по себе не означают выполнение задачи.

### 2.1. Входит в продукт

- Каталог произведений и получение описательных метаданных.
- Выбор фильмов, сезонов, эпизодов и спецматериалов.
- Требования к качеству, языкам и размещению дорожек.
- Поиск релизов у нескольких провайдеров.
- Объяснимое сопоставление релизов и файлов с запросом.
- Автоматический выбор и ручное разрешение неоднозначностей.
- Получение файлов через BitTorrent.
- Проверка медиапотоков и внешних дорожек.
- Управление исходниками, медиатекой и освобождением места.
- Экспорт названий, NFO и изображений для отдельного медиасервера.
- WebUI, API, фоновые задания, диагностика, резервное копирование.

### 2.2. Не входит в базовый продукт

- Видеоплеер, транскодирование и потоковый медиасервер.
- Эмуляция Jellyfin API, управление его клиентами и прогрессом просмотра.
- Сервис публичного обмена файлами и многопользовательский облачный хостинг.
- Изменение содержимого видео, перекодирование и автоматическое встраивание дорожек.
- Совместимость с внутренними интерфейсами старого Lazarr.
- Обязательная поддержка всех трекеров и всех способов доставки контента.

P2: другие протоколы загрузки, рекомендации, списки просмотра, уведомления во внешние сервисы, кластеризация.

## 3. Среда и пользователь

Рабочее допущение: один самостоятельно размещаемый экземпляр для владельца домашней медиатеки. Базовая целевая среда — Linux и Linux-контейнер, включая Unraid. Работа через Docker Desktop/WSL2 требует отдельной проверки файлового хранилища. Нативные Windows/macOS-приложения не обязательны.

AUTH-01. При первом запуске владелец создаёт администратора. Начальная настройка не должна оставаться доступной после завершения.

AUTH-02. Доступ к управлению, журналам, настройкам провайдеров и API требует аутентификации. Наличие приложения в локальной сети не отменяет проверку доступа.

AUTH-03. Поддерживаются вход, выход, смена пароля, завершение сессий и документированное восстановление доступа при локальном административном доступе к установке.

AUTH-04. Дополнительные пользователи и роли — P1. До их реализации все данные принадлежат одному экземпляру, а не имеют фиктивного разграничения по пользователям.

## 4. Основные пользовательские сценарии

| Сценарий | Ожидаемый результат |
| --- | --- |
| Первый запуск | Владелец настраивает провайдеры и хранилище, видит результаты проверок и может создать первую задачу |
| Добавить фильм | Выбирает конкретное произведение, профиль требований и способ выбора; получает проверенный фильм в библиотеке |
| Добавить сезон | Выбирает все или отдельные эпизоды; система может получить их из одной или нескольких раздач |
| Следить за сериалом | Вышедшие и будущие эпизоды обрабатываются согласно заданной области наблюдения |
| Найти альтернативу | Видит сравнение релизов и меняет источник без преждевременной потери рабочей версии |
| Исправить сопоставление | Связывает файл с эпизодом, выбирает дорожки и видит действующие исключения |
| Устранить ошибку провайдера | Исправляет настройки или проходит авторизацию; обработка продолжается без повторного создания задачи |
| Перезапустить приложение | Подтверждённые решения, файлы и загрузки сохраняются; незавершённая работа восстанавливается |
| Удалить задачу | Выбирает сохранение медиа либо удаление управляемых данных; видит влияние на другие задачи |
| Подключить Jellyfin | Получает понятную структуру библиотеки и инструкции по доступу к исходникам и опубликованным файлам |

## 5. Каталог и метаданные

CAT-01. Поиск произведений поддерживает название, оригинальное название, локализованные варианты и известный внешний идентификатор. Результаты различают фильмы, сериалы, годы и одноимённые произведения.

CAT-02. Карточка содержит доступные названия, описание, год, даты, постер, фон, жанры, страну, язык, внешние ID, участников и рейтинги. Неизвестные поля допустимы и не заполняются выдуманными значениями.

CAT-03. Для сериала доступны сезоны, эпизоды, спецматериалы, даты выхода и состояние продолжения. Метаданные могут дополняться постепенно; частичный сбой не уничтожает уже сохранённые сведения.

CAT-04. Каждое внешнее значение имеет источник и время получения. Пользовательское исправление хранится отдельно и имеет приоритет до явного сброса.

CAT-05. Внутренний ID произведения и эпизода не зависит от названия, пути или отображаемого номера. Обновление метаданных не создаёт новое произведение автоматически.

CAT-06. Один объект может иметь несколько внешних ID. Слияние конфликтующих объектов требует подтверждения; одинаковые названия не являются достаточным основанием.

CAT-07. Сохранённые карточки доступны при недоступности внешнего сервиса. Видны устаревание данных и ошибка обновления.

CAT-08. Предусмотрены ограничение частоты обновлений, кэш и ручное обновление. При массовом обновлении учитываются лимиты провайдера.

CAT-09. P1: создание произведения вручную и импорт локальных файлов, отсутствующих в каталогах.

## 6. Эпизоды, нумерация и календарь

NUM-01. Необходимо разделять идентичность эпизода, каноническую нумерацию, нумерацию источника и нумерацию экспорта. Смена отображения не меняет идентичность эпизода.

NUM-02. Поддерживаются обычная сезонная и абсолютная нумерация, специальные эпизоды, альтернативные группы сезонов, дробление сезона на части и сезон с самостоятельным названием.

NUM-03. Альтернативное соответствие хранится с источником и признаком достоверности. Неоднозначное соответствие не применяется автоматически.

NUM-04. Один файл может содержать несколько эпизодов; один эпизод может состоять из нескольких частей. Модель должна представлять оба случая. При неподдерживаемом формате экспорта система требует ручного решения и не выдаёт дубликаты файла за независимые эпизоды.

NUM-05. Год произведения, год сезона и дата конкретного эпизода имеют разное значение. Обозначение порядка показов не считается безусловным номером сезона.

NUM-06. Пользователь может задать соответствие номеров и порядок показа спецматериалов. Эти решения не стираются при обновлении каталога.

CAL-01. Дата выхода хранится с точностью: точный момент, календарная дата, месяц, год либо неизвестно. Дата без времени не превращается молча в точный момент полуночи UTC.

CAL-02. Моменты времени хранятся независимо от часового пояса отображения. Для приблизительных дат применяется явно описанная политика начала поиска.

CAL-03. Перенос премьеры меняет будущий план, но не отменяет уже проверенное медиа. Неизвестная дата не означает ни «уже вышло», ни «никогда не искать»: используется отдельная редкая проверка.

CAL-04. Наблюдение имеет явную область: выбранные эпизоды, текущий сезон, выбранные сезоны или всё произведение с будущими сезонами. Добавление новых спецматериалов задаётся отдельной настройкой.

## 7. Задачи и требования к результату

TASK-01. Задача объединяет произведение, выбранные элементы, профиль качества, правила автоматизации и наблюдения. Фильм или конкретный эпизод является самостоятельным элементом выполнения.

TASK-02. Создание одинакового запроса не должно приводить к независимой повторной загрузке без явного намерения пользователя. Совместимые задачи могут ссылаться на общий проверенный файл.

TASK-03. Доступны пауза, продолжение, поиск сейчас, повтор ошибки, ручной выбор, отклонение кандидата, смена требований и удаление.

TASK-04. Пауза наблюдения, пауза поиска и пауза сетевой загрузки имеют различимую семантику. Интерфейс показывает, что именно остановлено.

TASK-05. Изменение требований создаёт новую редакцию запроса. Выполняющаяся операция хранит редакцию, по которой запущена; устаревший результат не может молча заменить актуальный выбор.

TASK-06. Завершение всех текущих эпизодов не выключает наблюдение за будущими, если оно включено. Завершение задачи и завершение наблюдения — разные события.

REQ-01. Профиль разделяет обязательные условия и предпочтения. Обязательное нарушение нельзя компенсировать высоким рейтингом по другим признакам.

REQ-02. Настраиваются разрешение, допустимые видеокодеки, HDR/SDR, языки аудио, языки субтитров, встроенные/внешние дорожки, размер и приоритет источников. Отдельные свойства могут оставаться без ограничения.

REQ-03. Для каждого языка определяется логика: необходимы все указанные языки либо хотя бы один; субтитры обязательны или желательны; допустимы ли внешние дорожки. Значения по умолчанию отображаются пользователю.

REQ-04. P1: предпочтения студий озвучивания, релиз-групп, числа каналов и типа субтитров. Неизвестное свойство не следует выдавать за подтверждённое.

REQ-05. Есть два режима автоматизации: автоматический выбор подходящего релиза и выбор только пользователем. Автоматическое улучшение уже готовой версии — P1, с отдельными правилами расхода места и замены.

REQ-06. При изменении профиля пользователь видит область применения: новые элементы, незавершённые элементы или также переоценка готовых. Готовые файлы не удаляются только из-за изменения профиля.

## 8. Провайдеры и внешние интеграции

PROV-01. Разделяются провайдеры метаданных, поиска релизов и дат выхода. Один внешний сервис может реализовывать несколько возможностей.

PROV-02. Каждый провайдер сообщает стабильный ID, версию, поддерживаемые операции, настройки, требования авторизации и ограничения. Отсутствие возможности отличается от временной ошибки.

PROV-03. Для контент-провайдера нужны операции поиска с пагинацией, чтения подробностей, получения источника загрузки, проверки состояния и управления авторизацией.

PROV-04. Результат поиска содержит ID релиза, название, ссылку, доступные технические сведения, размер, доступность источников, ревизию и свидетельства. Провайдер не принимает окончательное решение о соответствии эпизоду.

PROV-05. Авторизация поддерживает сохранение сессии, истечение, повторный вход, выход и интерактивный challenge. Пароли и cookies не возвращаются в обычном ответе настроек.

PROV-06. Ошибки имеют устойчивые категории: неверная конфигурация, требуется вход, требуется действие пользователя, ограничение частоты, недоступность, отсутствие объекта, ошибка формата и неподдерживаемая операция.

PROV-07. Применяются таймауты, ограниченная конкурентность, паузы после ошибок и соблюдение времени повторной попытки. Сбой одного провайдера не отменяет результаты остальных.

PROV-08. Поддерживаются зеркала и изменяемый базовый адрес без потери идентичности релиза. Приватные URL с ключами не попадают в журналы и экспорт диагностики.

PROV-09. Интеграция с браузерным помощником для разрешённых сессий с challenge выполняется через явный контракт. HTML-ответ нельзя принять за torrent-файл; размер и тип ответа проверяются.

PROV-10. Начальный предлагаемый набор: TMDB для метаданных, Rutracker, Kinozal и Nyaa для релизов. Этот список требует подтверждения и не означает, что конкретные API или способы доступа уже выбраны.

PROV-11. Обязательны контрактные тесты на локальных фикстурах, включая неполные ответы, необычные кодировки и изменённую структуру страницы. Живые интеграционные проверки выполняются отдельно.

PROV-12. P1: независимо обновляемые адаптеры. Формат расширений выбирается отдельно; совместимость с Python-плагинами не требуется. Если расширение выполняет код, нужны модель доверия, ограничение полномочий, проверка совместимости, происхождения пакета и откат. Одна контрольная сумма не подтверждает доверенный источник.

## 9. Поиск релизов

SEARCH-01. Поисковые запросы строятся из ID, названий, алиасов, года и допустимых схем нумерации. Пользователь может просмотреть фактически использованные запросы.

SEARCH-02. Поиск имеет бюджет: количество запросов, страниц, подробных проверок и общее время. Бюджеты настраиваются и учитывают ограничения отдельных провайдеров.

SEARCH-03. Результаты дедуплицируются по достоверным идентификаторам. Совпадение названия недостаточно для объединения, а один infohash на разных сайтах не теряет сведения об источниках.

SEARCH-04. Проверки выполняются от дешёвых к дорогим: поисковая выдача, подробности релиза, состав файлов, фактические потоки. Точные этапы и веса текущего Lazarr переносить не требуется.

SEARCH-05. Ранее использованный обновляемый релиз может проверяться первым. Новая серия подтверждается актуальной ревизией файлов, а не старым заголовком темы.

SEARCH-06. Сохранённые результаты имеют срок актуальности и версию оценивания. Повторный поиск не должен бесконечно разбирать тот же неизменившийся ответ.

SEARCH-07. Пользователь видит время поиска, проверенные источники, ошибки и достигнутые ограничения. Формулировка «лучший» означает лучший из проверенных кандидатов, а не всего интернета.

SEARCH-08. Отказ пользователя от кандидата сохраняется с областью действия. Повторная рекомендация возможна только по явной политике, например при новой ревизии, и объясняется.

SEARCH-09. Отсутствие результатов, недоступность провайдеров и недостаточность доказательств отображаются как разные исходы.

## 10. Сопоставление и объяснение решений

MATCH-01. Сопоставление является самостоятельной предметной функцией: вход — запрос, сведения о произведении, релизе и файлах; выход — решение по каждому элементу, связанные файлы, основания и ограничения.

MATCH-02. Для каждого критерия возможны три результата: подтверждено, опровергнуто, неизвестно. Неизвестное не равно отсутствию и не равно соответствию.

MATCH-03. Свидетельство хранит свойство, значение, источник, исходный фрагмент, область действия, полноту перечисления и ревизию. Заявление обо всей раздаче нельзя автоматически распространить на каждый файл.

MATCH-04. Проверяются идентичность произведения, тип содержимого, сезон/эпизод, соответствие файла и обязательные свойства качества. Явный конфликт внешних ID блокирует автоматический выбор.

MATCH-05. Парсер названий поддерживает распространённые сезонные и абсолютные обозначения, диапазоны, мультисезонные сборники, спецэпизоды, несколько эпизодов в одном файле и ненумерованные фильмы.

MATCH-06. Числа разрешения, года, кодека, контрольной суммы и номера релиза не должны приниматься за номера эпизодов без контекста. Образцы, трейлеры, обложки и служебные файлы не считаются основным видео.

MATCH-07. Название сезона и год могут уточнять неоднозначность, но не переписывают явное противоречащее соответствие файлов без объяснимого правила.

MATCH-08. Повтор одного утверждения в нескольких полях не создаёт независимых доказательств. При конфликте фактических потоков и описания побеждает фактическое свойство файла.

MATCH-09. Подбор внешних аудио и субтитров учитывает эпизод, имя, каталог, язык и тип дорожки. При нескольких равноправных вариантах требуется выбор, а не случайное связывание.

MATCH-10. Результат отдельно показывает пригодность кандидата для получения и готовность файла для публикации. Неизвестные до получения технические свойства могут разрешать ограниченную проверочную загрузку по политике, но не пометку «проверено».

MATCH-11. Ранжирование применяется только после проверки блокирующих условий. При одинаковых входных данных и версии правил результат воспроизводим; равенство разрешается стабильным правилом.

MATCH-12. Неоднозначная идентичность или привязка эпизода блокирует автоматический выбор. Интерфейс предлагает ручное сопоставление и показывает причины.

MATCH-13. Ручное исключение привязано к конкретному элементу, релизу/ревизии и критерию. Оно не становится глобальным доказательством. Небезопасные пути, повреждённый контейнер и нарушение целостности не обходятся исключением качества.

MATCH-14. Отчёт позволяет ответить: почему выбран этот релиз, почему отклонён другой, какие свойства подтверждены файлами, какие заявлены источником и что ещё предстоит проверить.

## 11. Получение файлов

DL-01. Поддерживаются torrent-файл и magnet-ссылка, получение метаданных, выбор файлов, приоритеты, пауза, продолжение, отмена и восстановление после перезапуска.

DL-02. Загрузка — отдельный объект, а не часть одной задачи. Несколько эпизодов и задач могут использовать одну раздачу. Удаление одного потребителя не удаляет данные остальных.

DL-03. План загрузки содержит неизменяемую привязку к ревизии источника и выбранным индексам файлов. Изменение темы на трекере создаёт новую ревизию, а не переписывает работающий план.

DL-04. Основное видео и необходимые внешние дорожки выбираются совместно. Посторонние файлы не включаются намеренно; технические дополнительные байты на общих torrent-частях допустимы и учитываются в расходе места.

DL-05. Поддерживаются лимиты скорости, числа одновременных загрузок и раздач, параметры сетевого порта и политика сидирования. Соблюдаются private-флаги раздач и ограничения применяемого протокола.

DL-06. Интерфейс показывает полученные и требуемые байты, скорость, доступность пиров, ошибки, выбранные файлы и приблизительное оставшееся время. Неизвестная оценка времени не отображается как ноль.

DL-07. Зависшие загрузки определяются по политике, а не только по отсутствию мгновенной скорости. Повтор, смена источника или запрос действия пользователя имеют ограничение числа попыток.

DL-08. При нехватке места загрузка безопасно приостанавливается. При потере точки монтирования приложение не начинает писать в одноимённый каталог системного диска.

DL-09. Состояние движка и приложение согласуются после аварии. Возобновление не предполагает целостность файла только по наличию пути и размеру.

DL-10. Система различает завершение выбранных файлов, завершение всей раздачи и окончание сидирования.

DL-11. Выбор движка — техническое исследование. Полностью Rust-движок, FFI и отдельный процесс сравниваются по корректности, возобновлению, private-трекерам, выборочной загрузке, поддержке и лицензиям. Требование «сервер на Rust» само по себе не означает запрета внешнего движка.

## 12. Проверка медиа

VERIFY-01. Проверяются открываемость контейнера, наличие основного видеопотока, разрешение, кодеки, длительность, аудио и субтитры. Полная декодирующая проверка каждого кадра не является обязательным условием P0.

VERIFY-02. Внешние дорожки проверяются как самостоятельные файлы и как часть привязки к видео. Нечитаемый файл не считается доступным только по расширению.

VERIFY-03. Заявление провайдера и фактический результат сохраняются раздельно. Неопределённый язык потока остаётся неопределённым; имя файла может быть отдельным свидетельством, а не результатом фактического анализа языка речи.

VERIFY-04. Проверка ограничивается по времени, памяти, объёму вывода и числу параллельных процессов. Ошибка анализатора не должна останавливать API или другие загрузки.

VERIFY-05. Технический таймаут, неполный файл, повреждение, неподходящее качество и неопределённые свойства имеют разные причины и способы повтора.

VERIFY-06. После изменения файла либо выбора новой версии прежний результат не используется как актуальный без проверки его привязки к содержимому.

VERIFY-07. Публикация разрешается только после выполнения обязательных требований или конкретных допустимых ручных исключений. «Скачано» и «проверено» — разные состояния.

## 13. Просмотр до завершения загрузки

Рабочее решение для P0: публиковать полностью полученные и проверенные файлы. Это продуктовый выбор для новой версии, требующий подтверждения, а не требование сохранить прежнее поведение.

PARTIAL-01. P1: предварительная готовность к просмотру реализуется отдельной возможностью и отдельно принимается. Размер sparse-файла и наличие его имени не доказывают доступность байтов для плеера.

PARTIAL-02. Необходимо определить поддерживаемые контейнеры, наличие служебных структур, начальный буфер, стратегию частей и поведение при обращении к отсутствующим данным.

PARTIAL-03. Частичная готовность, полная загрузка и полная проверка показываются независимо. Пользователь должен видеть ограничения перемотки.

PARTIAL-04. Простая файловая ссылка не считается достаточным решением для произвольного плеера. Требуется испытать выбранную схему с медиасервером; если надёжность требует собственного шлюза чтения, отдельно пересмотреть границы продукта.

## 14. Хранилище и публикация библиотеки

STORE-01. Разделяются оригинальные файлы источника и пользовательская структура библиотеки. Раздача сохраняет исходные имена, необходимые движку.

STORE-02. Система управляет только зарегистрированными файлами и созданными ею объектами. Она не присваивает и не удаляет посторонние файлы по совпадению пути или имени.

STORE-03. Корни хранилища настраиваются и проверяются на доступность, права, свободное место и выбранные возможности файловой системы. Несколько корней — P1; модель не должна препятствовать их добавлению.

STORE-04. Для публикации выбирается одна документированная стратегия: относительные символические ссылки, жёсткие ссылки либо явное копирование. Нельзя молча переключаться на копирование больших файлов. Рабочий вариант — относительные ссылки с доступностью всего общего корня медиасерверу.

STORE-05. Формат библиотеки различает фильмы, сериалы и аниме-сериалы; аниме-фильм остаётся фильмом. Автоматическую классификацию можно исправить вручную.

STORE-06. Имена нормализуются с учётом запрещённых символов, длины, Unicode, регистра и коллизий. Разные произведения с одинаковым названием не должны перезаписывать друг друга.

STORE-07. Публикация и замена проходят через подготовку, проверку и переключение. Последняя рабочая версия остаётся доступной до готовности новой. В пределах поддерживаемой файловой системы переключение выполняется атомарно либо восстанавливается по журналу.

STORE-08. База и файловая система не считаются одной транзакцией. Каждая многошаговая операция имеет устойчивый журнал и повторяемые шаги восстановления.

STORE-09. Фоновая сверка выявляет отсутствующие исходники, сломанные ссылки, устаревшие публикации и незаконченное удаление. Отсутствующий диск означает проблему хранилища, а не разрешение на массовую очистку записей.

STORE-10. Изменение корня для новых загрузок не переносит старые данные автоматически. Перенос — отдельная явная операция с оценкой места, прогрессом и восстановлением после прерывания; P1.

STORE-11. Изменение данных через ссылку может менять исходник. Это свойство объясняется в документации; рекомендуется доступ медиасервера только на чтение.

STORE-12. Учёт места различает логический размер файлов, реально выделенные байты, дополнительные копии и общий исходник нескольких публикаций. Жёсткие ссылки не учитываются как независимые копии.

## 15. Метаданные библиотеки и Jellyfin

EXPORT-01. Экспортируются названия, выбранная нумерация, NFO фильма/сериала/сезона/эпизода, постеры, фоны и изображения эпизодов при наличии исходных данных.

EXPORT-02. Имена видео, координаты в NFO и выбранная схема нумерации согласованы. Нельзя назначить другой сезонный ID только из-за совпадения номера альтернативной схемы.

EXPORT-03. Для спецматериалов поддерживается порядок показа, вычисленный по датам или заданный вручную. При неоднозначности позиция остаётся незаданной.

EXPORT-04. Отсутствующие поля опускаются. Неизвестная длительность и рейтинг не экспортируются как нули. Описательная длительность и измеренная длительность видео различаются.

EXPORT-05. Изображения и текстовые метаданные записываются безопасно; неизменившийся контент не перезаписывается. Сбой загрузки изображения сохраняет предыдущий пригодный файл и не блокирует публикацию видео.

EXPORT-06. Документация описывает подключение библиотек, монтирование нужных корней и распределение ответственности за метаданные. Совместимость проверяется на закреплённой версии Jellyfin; конкретная версия выбирается при реализации.

EXPORT-07. P1: запрос обновления библиотеки через API Jellyfin с отдельными настройками доступа. Ошибка Jellyfin не отменяет успешную локальную публикацию.

## 16. Удаление, замена и владение файлами

DELETE-01. Раздельно доступны: прекратить наблюдение; удалить задачу с сохранением медиа; удалить публикацию; удалить управляемые исходники. Интерфейс не объединяет их в неясное «Удалить».

DELETE-02. До подтверждения удаления данных показываются затронутые элементы, общие потребители и ожидаемое освобождение места. Обычные обратимые действия не требуют лишних подтверждений.

DELETE-03. Исходник нельзя удалить, пока он нужен другой задаче, публикации, проверке или действующей политике сидирования, без явного разрешения конфликтов.

DELETE-04. Перед удалением исходника снимаются управляемые публикации. Ошибка на любом этапе оставляет восстанавливаемую операцию, а не ложный статус успеха.

DELETE-05. Очистка кэша, незавершённых ненужных загрузок и окончательно удалённого медиа имеет разные политики. Кэш не включает единственную копию пользовательского файла.

DELETE-06. Автоматическое улучшение качества не уничтожает последнюю проверенную версию до проверки замены. Период хранения предыдущей версии и лимит места задаются явно.

## 17. Модель состояний и фоновые процессы

Нельзя выразить всё состояние одним полем задачи. Требуются как минимум независимые состояния запроса, получения файла, проверки, публикации и наблюдения.

| Объект | Пример состояний |
| --- | --- |
| Элемент запроса | ожидает даты, ожидает поиска, ищется, нужен выбор, источник выбран, выполнен, приостановлен, отменён |
| Загрузка | ожидает метаданных, в очереди, получает файлы, приостановлена, выбранные файлы получены, сидируется, остановлена, ошибка |
| Проверка | не запускалась, ожидает данных, выполняется, успешна, несоответствие, техническая ошибка |
| Публикация | отсутствует, подготавливается, опубликована, заменяется, недоступна, удаляется |
| Фоновое задание | ожидает, выполняется, ожидает повтора, завершено, отменено, исчерпаны попытки |

STATE-01. Для каждого перехода определяются причина, инициатор, предусловия, побочные эффекты и способ восстановления. Примеры выше — семантика, а не обязательные названия enum.

STATE-02. Состояние задачи агрегируется из элементов; частичный успех не скрывает неготовые серии. В интерфейсе доступно ближайшее требуемое действие.

JOB-01. Долгая работа выполняется устойчивыми заданиями: обновление метаданных, поиск, получение подробностей, получение источника, проверка файлов, публикация, очистка и сверка.

JOB-02. Задание хранит тип, объект, редакцию входа, время запуска, число попыток, ошибку и срок владения исполнителем. Перезапуск возвращает потерянную работу в обработку.

JOB-03. Предполагается повторное выполнение после сбоя. Побочные эффекты идемпотентны либо защищены журналом; обещание выполнения «ровно один раз» не является проектным допущением.

JOB-04. Есть раздельные ограничения конкурентности для сети, диска, технического анализа и конкретных провайдеров. Длинная операция не блокирует интерфейс и другие независимые задания.

JOB-05. Повторы имеют задержку, случайный разброс и предел. Требование авторизации или неверный путь не порождает бесконечный быстрый цикл.

JOB-06. Отмена кооперативна и проверяется между значимыми шагами. Результат отменённого или устаревшего задания не публикуется как актуальный.

JOB-07. Выключение прекращает принятие новой работы, сохраняет прогресс и ограниченно ожидает исполнителей. Принудительное завершение также входит в поддерживаемые сценарии восстановления.

## 19. API и пользовательский интерфейс

### 19.1. API

API-01. WebUI работает через документированный API. Минимальные группы: авторизация, каталог, задачи, профили, поиск/кандидаты, сопоставление, загрузки, хранилища, провайдеры, задания и диагностика.

API-02. Долгая операция возвращает идентификатор задания. HTTP-соединение не удерживается до окончания многоминутного поиска или проверки.

API-03. Нужны стабильные машинные коды ошибок, понятный текст, идентификатор запроса и ошибки полей. Внутренние стеки и секреты клиенту не возвращаются.

API-04. Списки поддерживают пагинацию и стабильную сортировку. Изменения настроек и выбора защищены от незаметной потери параллельного редактирования.

API-05. Повтор создания или команды после сетевого сбоя не дублирует побочный эффект: для подходящих операций используется ключ идемпотентности либо эквивалентная семантика.

API-06. Поток обновлений через SSE/WebSocket или опрос передаёт состояние и прогресс. После разрыва клиент может восстановить актуальную картину; пропущенное событие не означает потерю состояния.

API-07. Спецификация запросов, ответов, ошибок и авторизации входит в поставку. Старые маршруты Lazarr не являются обязательными.

API-08. Минимальная проверка живости не раскрывает настройки. Проверка готовности отдельно сообщает, может ли процесс обслуживать работу с БД и очередью; недоступность одного внешнего трекера не делает весь экземпляр «мёртвым».

### 19.2. WebUI

UI-01. Основные экраны: начальная настройка, обзор, поиск произведений, карточка произведения, задачи, подбор релиза, сопоставление файлов, загрузки, библиотека, настройки и диагностика.

UI-02. Обзор показывает происходящее сейчас, требуемые действия пользователя, готовые элементы, ошибки хранилища и ближайшую работу.

UI-03. В подборе релиза доступны сравнение требований, оснований выбора, состава файлов, дорожек, неизвестных свойств и причин отклонения.

UI-04. Ручное сопоставление показывает таблицу «элемент → видео → дорожки → экспортируемое имя», конфликты и последствия до сохранения.

UI-05. Пользователь видит разницу между отсутствием результата, ожиданием премьеры, паузой, недоступностью сервиса и требованием ручного действия.

UI-06. Секретное поле не подставляет сохранённый пароль в браузер. Различаются «оставить прежнее», «заменить» и «удалить».

UI-07. Интерфейс пригоден для мобильного браузера и клавиатуры, имеет подписанные элементы управления и не обозначает статус только цветом. Русский язык — обязательный; подготовка к локализации — P1.

UI-08. Загрузка страницы не должна ждать внешнего провайдера. Сохранённые данные показываются сразу, обновление — отдельно с состоянием выполнения.

## 20. Безопасность и эксплуатационная надёжность

SEC-01. Пароли хранятся как стойкие парольные хеши; сессии имеют срок действия, безопасные cookie и отзыв. Cookie-аутентификация защищена от CSRF; HTML и внешние строки — от XSS.

SEC-02. Учётные данные провайдеров защищаются отдельным ключом. Документируются размещение ключа, резервирование и последствия утраты. Секреты не попадают в историю событий и обычные резервные выгрузки без явной политики.

SEC-03. Путь из torrent-метаданных или ответа провайдера недоверенный: запрещены выход за корень, абсолютные пути и обход через ссылки. Проверка строкового префикса пути недостаточна.

SEC-04. Внешние команды запускаются без сборки shell-строк из пользовательских значений. Ответы сети, архивы, изображения и метаданные имеют ограничения размера и времени обработки.

SEC-05. Исходящие запросы следуют сетевой политике: доверенные административные адреса локальных интеграций отличают от URL из непроверенных метаданных; проверяются перенаправления и доступ к служебным адресам.

SEC-06. При наличии прокси явно задаются доверенные посредники, внешний URL и базовый путь. Заголовки от произвольного клиента не определяют доверенный адрес пользователя.

SEC-07. Ошибка одного задания, адаптера или файла локализуется. Выполнение недоверенных расширений в адресном пространстве основного процесса не считается изоляцией.

OPS-01. Структурированные журналы связывают запрос, задачу, элемент, релиз и фоновое задание. Уровень детализации настраивается, объём ограничивается.

OPS-02. Доступны длительность и размер очереди, частота ошибок провайдеров, повторы, скорость загрузки, длительность проверки, свободное место и ошибки публикации.

OPS-03. Диагностический архив исключает секреты и предупреждает о потенциально личных названиях и путях. Экспорт запускается явно.

OPS-04. Резервная копия включает согласованное состояние БД, настройки, ручные соответствия и необходимые ключи по выбранной защищённой процедуре. Медиа, кэш и повторно создаваемые файлы описаны отдельно.

OPS-05. Восстановление проверяется практическим сценарием на чистой установке. Простого наличия кнопки «Создать копию» недостаточно.

## 21. Технические границы реализации на Rust

Это ограничения качества архитектуры, а не выбранный набор библиотек.

RUST-01. Предметные правила, API, планировщик и управление состоянием реализуются на Rust. Проверка контейнеров и торрент-движок могут быть внешними компонентами, если это отдельно принято.

RUST-02. Предметное ядро не зависит от HTTP, конкретной БД, трекера или торрент-библиотеки. Сопоставление и принятие решений можно проверять на данных без сети и диска.

RUST-03. Явно выделяются границы каталога, задач, поиска, сопоставления, загрузки, проверки, хранения и публикации. Для первой версии предпочтителен один развёртываемый сервер; микросервисы не являются требованием.

RUST-04. Асинхронные операции не выполняют блокирующую работу в потоке обслуживания запросов. FFI, анализ медиа и тяжёлый разбор имеют ограниченные исполнители.

RUST-05. Типы различают ID разных сущностей, неизвестные значения, области свидетельств, редакции и допустимые состояния. Недопустимые переходы не маскируются произвольными строками.

RUST-06. Отсутствуют неограниченные очереди, бесконечные повторы без паузы и штатные panic на внешнем вводе. Unsafe/FFI изолированы и имеют документированные условия корректности.

RUST-07. Зависимости фиксируются, лицензии учитываются, сборка воспроизводима. Поддерживаемая версия Rust и целевые архитектуры задаются при выборе инструментов.

RUST-08. Решения о web-фреймворке, БД, frontend, движке загрузки и расширениях оформляются отдельными краткими записями: требования, варианты, проверка, выбранный вариант и последствия. Этот документ не выбирает их без исследования.

## 22. Установка, обновление и переход

DEPLOY-01. Нужны контейнерный образ, пример Compose, описание постоянных каталогов, портов, UID/GID, часового пояса и прав. Настройки и медиа переживают пересоздание контейнера.

DEPLOY-02. Обязательная архитектура P0 — Linux x86-64; ARM64 — предлагаемый P1. Образ не требует привилегированного режима для обычной работы.

DEPLOY-03. Первый запуск валидирует конфигурацию и хранилище. Ошибка не должна запускать разрушительную «починку» неизвестных данных.

DEPLOY-04. Обновление включает проверку совместимости, резервирование необходимых данных и миграцию схемы. Несовместимое понижение версии отклоняется с понятной причиной; откат выполняется через совместимую копию.

DEPLOY-05. Поддерживаются корректные сигналы завершения и диагностика контейнера. Ошибка одного внешнего сервиса не вызывает бесконечный цикл перезапуска приложения.

MIG-01. Отказ от старой архитектуры не определяет автоматически судьбу пользовательской медиатеки. Совместимость на уровне пользовательских данных принимается отдельным решением.

MIG-02. Рабочий минимум — установка с чистой БД, при которой старые данные остаются нетронутыми. Два менеджера не должны одновременно управлять одним writable-хранилищем.

MIG-03. P1, если подтверждён переход существующих пользователей: одноразовый импорт намерений пользователя, профилей, ручных соответствий и доступного медиа через документированный формат. Перенос внутренних очередей и старых отчётов не обязателен.

MIG-04. Импорт сначала выполняется в режиме предварительного отчёта: что распознано, что конфликтует и что не поддерживается. Оригиналы не переносятся и не удаляются без отдельной операции.

## 23. Проверки и критерии приёмки

### 23.1. Обязательные сквозные сценарии

| ID | Условия | Критерий успеха |
| --- | --- | --- |
| A01 | Чистая установка | Владелец проходит настройку и получает первый фильм в библиотеке |
| A02 | Два одноимённых фильма разных лет | Автоматически выбирается только подтверждённое произведение; при нехватке данных нужен выбор |
| A03 | Сезонный пак и одиночные серии | Все выбранные эпизоды получены без потери привязок и ненужных независимых загрузок |
| A04 | Аниме с альтернативной нумерацией | Идентичность, файл и экспортируемый номер согласованы; обновление каталога не теряет ручные связи |
| A05 | Язык заявлен для релиза, но отсутствует в одном видео | Этот эпизод не публикуется как удовлетворяющий обязательному языку |
| A06 | Неизвестный язык и несколько внешних дорожек | Система сохраняет неопределённость и предлагает разрешить её; случайного назначения нет |
| A07 | Провайдер ограничил запросы | Соблюдается пауза, остальные провайдеры работают, причина видна |
| A08 | Провайдер потребовал повторный вход | Задача сохраняется и продолжается после авторизации |
| A09 | Обновилась тема с новой torrent-ревизией | Новый поиск видит новые файлы, текущая загрузка сохраняет прежний план |
| A10 | Принудительное завершение при загрузке и публикации | После запуска нет дубликатов и потери подтверждённого выбора; операции восстановлены |
| A11 | Закончился диск или пропало монтирование | Запись безопасно остановлена, посторонние данные и записи библиотеки не удалены |
| A12 | Две задачи используют общий исходник | Удаление первой не повреждает вторую; окончательное удаление освобождает данные по политике |
| A13 | Новая версия не прошла проверку | Прежняя проверенная публикация остаётся доступной |
| A14 | На целевом пути лежит чужой файл | Он не перезаписывается; конфликт виден пользователю |
| A15 | Изменились требования во время поиска | Устаревший результат не становится актуальным выбором |
| A16 | Восстановление резервной копии | Сохраняются задачи, настройки, ручные связи; отсутствующее медиа корректно диагностируется |
| A17 | Jellyfin читает библиотеку | Фильмы, сезоны, серии, дорожки и метаданные распознаны согласно экспортируемой схеме |
| A18 | Внешний ввод содержит опасный путь или HTML | Нет выхода за хранилище, исполнения кода или раскрытия секретов |
| A19 | Один файл содержит несколько эпизодов | Покрытие показано точно, неподдерживаемый экспорт требует решения без ложного завершения |
| A20 | Сбой изображения или каталога метаданных | Сохранённые данные доступны, готовое видео не теряется |

### 23.2. Наборы проверок

- Модульные: требования, нормализация, нумерация, сопоставление, ранжирование, переходы состояний.
- Проверки свойств: повторяемость, отсутствие усиления дублированных свидетельств, невозможность обхода обязательного конфликта рейтингом.
- Контрактные: каждый адаптер, движок загрузки, анализатор медиа и хранилище.
- Интеграционные: БД, очередь, публикация, совместное использование файлов, авторизация и API.
- Аварийные: завершение процесса между файловыми шагами, таймауты, заполненный диск, исчезновение монтирования, повреждённые ответы и восстановление.
- Fuzzing: внешние имена, torrent-метаданные, парсеры номеров и границы обработки недоверенного ввода.
- Сквозные UI: настройка, создание задачи, ручной выбор, исправление сопоставления, замена и удаление.
- Совместимость: принятая файловая система, контейнерное окружение и закреплённая версия Jellyfin.

Тестовые данные должны включать неоднозначные случаи, а ожидаемый результат — утверждаться по смыслу произведения и файлов, а не копироваться из ответа старого движка. Регрессионная база примеров может использовать реальные обезличенные названия; сетевой доступ и пользовательские учётные данные не требуются для базового CI.

### 23.3. Производительность

Предлагаемые исходные цели, которые надо подтвердить измерениями на стенде: 4 CPU, 8 GiB RAM, SSD; 1 000 задач, 20 000 элементов, 100 000 сохранённых кандидатов и 10 активных загрузок.

- P95 чтения локального состояния API — до 300 мс без учёта внешней сети.
- P95 принятия фоновой команды — до 500 мс; это время постановки, а не завершения работы.
- Отображение изменения локального состояния — до 2 секунд при исправном соединении.
- API остаётся доступен при параллельной технической проверке файлов и обновлении метаданных.
- Поведение памяти, очередей и журналов ограничено и проверено 24-часовым прогоном; нет роста пропорционально числу уже завершённых заданий без retention.
- Запуск API не ожидает полной пересверки большой медиатеки: восстановление показывает прогресс в фоне.

Методика измерений фиксирует состав файлов, размер торрент-кэша, конкурентность и конфигурацию. Целевые расходы RAM, скорость загрузки и время полного восстановления определяются после выбора движка; этот документ не обещает их без измерений.

5. Контейнер, Compose и руководство установки/обновления.
6. Инструкции хранилища, Jellyfin, резервирования и восстановления.

9. Средства импорта только если совместимость включена в утверждённый объём.
