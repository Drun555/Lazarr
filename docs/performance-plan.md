# План устранения регрессии производительности

## База сравнения — 23 сентября 2026

`git pull --ff-only` обновил main с `731469e` до `3e53408`. На Unraid уже
работает `drun555/lazarr:sha-3e53408`. В этой версии есть `JellyfinDtoBatch`:
часть N+1 уже устранена, но область пакетной загрузки слишком широка.

Проверки выполнены через HTTP учёткой lazarr-local и через SSH. В базе Unraid
15 произведений, 313 эпизодов, 132 LibraryAsset. Базу не копировали, контейнер
не перезапускали, кэш рабочего процесса не очищали. Внутренний профиль запускали
отдельным процессом с SQLite `mode=ro`, без миграций и фонового scheduler.

### Подтверждённые внутренние затраты

- `item_dto` одного эпизода: 1,053 с под cProfile, 36 SQL-запросов.
  `_load_playables` — 0,774 с, `playable_path` вызван 134 раза,
  всего 1330 `lstat` (0,346 с). Пакет проверяет всю библиотеку ради одного элемента.
  `library.detail` дополнительно строит все эпизоды сериала.
- `list_tasks`: 412 SQL-запросов, 1,185 с под cProfile;
  SQLAlchemy `_execute_internal` суммарно 0,743 с, sqlite execute 0,184 с.
  То есть проблема не только в скорости диска: много ORM-запросов/сборки объектов.
- `library.detail(6)`: 24 SQL-запроса, 0,239 с, 32 вызова `_version`,
  256 `lstat`. Это стоимость всего сериала, даже когда нужен один эпизод.
- Холодный NextUp в отдельном процессе выполнял `ffmpeg` для неизвестных языков
  субтитров и не завершился за минуту. Профиль прерван SIGINT, полный timing
  не получен. Стек: `next_up → batch.detail → library.detail → _version →
  detect_subtitle_language → subprocess.run`. Кэш `lru_cache(256)` только
  в памяти процесса; один stream может ждать timeout 15 секунд.

## Bottleneck по сценариям

1. **Главная Jellyfin:** NextUp строит DTO эпизодов всех сериалов *до* проверки
   наличия истории просмотра, фильтрации и пагинации. Latest/Items также строят
   богатые DTO с файловыми проверками. Тяжёлая синхронная работа идёт в async
   handlers одного Uvicorn worker. Главная WebUI легче, но tasks имеет N+1.
2. **Карточка медиа:** агрегаты сериалов требуют detail/файлов, batch загружает
   глобальные playable-данные. WebUI дополнительно вызывает `list_tasks()`
   целиком, чтобы найти одну задачу. Каждые 3 секунды UI повторяет загрузку
   downloads и открытой карточки; tasks опрашиваются каждые 10 секунд.
   Async `setInterval` не предотвращает наложение медленных запросов.
3. **Карточка эпизода:** глобальный playable scan + detail целого сериала,
   затем probe ресурсов. Измеренный PlaybackInfo на прогретых данных намного
   быстрее карточки: нельзя объяснять всю задержку собственно воспроизведением.

## Тяжёлые операции и место исполнения

| Операция | Сейчас | Предлагаемое место / хранение |
| --- | --- | --- |
| Язык субтитров | ffmpeg + langdetect внутри DTO/detail; process LRU | После верификации asset, ограниченный background worker; durable результат, включая `und`/ошибку и backoff |
| Metadata enrichment | `enrich/enrich_media` в GET, общий refresh_lock, обращения к провайдеру | Очередь после импорта/миграции/устаревания; отдавать последнее сохранённое состояние |
| Chapters, external audio probe | `ensure_probe` в карточке/PlaybackInfo | После готовности asset; single-flight, версионированный probe и retry |
| Extras discovery | Сканирование plan/files и probe при открытии | После завершения/изменения download, сохранять индекс extras |
| Проверка playable-путей | resolve/stat всей библиотеки на запрос | Ограничивать IDs текущего запроса; индекс доступности с TTL и событиями изменения |
| NextUp/Resume/счётчики | Сборка богатых DTO перед отбором | Отбор IDs/агрегаты SQL, DTO только результата; пользовательские данные отдельно |
| Субтитры/главы/trickplay/attachments | ffmpeg по запросу, файловый кэш, 2 workers | Популярные ресурсы прогревать фоном, остальные lazy single-flight; отдельный бюджет CPU/IO |
| Очистка resource cache | Перебор и stat файлов после cache miss | Периодическая фоновая уборка и квота |
| Tasks/scheduler/downloads polling | Большие снимки, повторные запросы | Пакетные SQL, scoped task read, лёгкий summary/change revision; polling без наложения |

Торрентные проверки, matcher, поиск провайдеров и Telegram уже имеют фоновые
пути, но конкурируют за CPU/SQLite/диски. В следующем прогоне измерить их
влияние отдельно: idle против download/search/verification. Нет оснований
объявлять их главным виновником без этих замеров.

## Порядок исправлений

### P0: убрать блокировки и лишнюю работу из чтения

1. Запретить ffmpeg/langdetect в catalog/detail GET. Персистентный результат
   определения языка вычислять после asset verification; старую библиотеку
   обработать низкоприоритетной возобновляемой очередью. Пока нет результата —
   `und`, не блокировать открытие.
2. Ограничить `JellyfinDtoBatch` областью выбранных media/episode/asset IDs.
   Не исправлять N+1 полной загрузкой всех файлов. Для карточки эпизода сделать
   точечный read model без detail всего сериала.
3. NextUp сначала отбирает просмотренные сериалы и следующий доступный episode
   ID, затем строит DTO. Пустая история должна быстро возвращать пустой результат.
   Items/Latest: фильтры, сортировка и страница до тяжёлой гидратации;
   сохранить корректные TotalRecordCount и пользовательские фильтры.
4. Пакетно загрузить связи `list_tasks`; карточке дать выборку одной задачи.
5. Оставшиеся sync SQL/filesystem/DTO выполнять вне event loop с ограничением
   concurrency. Это мера изоляции, не замена уменьшению числа операций.
   Не добавлять Uvicorn workers: процесс владеет scheduler/libtorrent и instance lock.

### P1: фоновая подготовка и управление свежестью

- Единая durable очередь: asset ID, тип работы, signature, статус, attempts,
  retry_at, ошибка; дедупликация и восстановление после рестарта.
- Signature: asset/version + size/mtime_ns + stream index + версия алгоритма.
  Замена/удаление файла, sidecar или probe инвалидирует связанные результаты.
- Availability можно кратко кэшировать, но перед выдачей/стримингом файла
  повторно проверять путь и ограничения безопасности. Нельзя убрать защиту
  от traversal/symlink ради сокращения `stat`.
- Общие метаданные отделить от progress/favorite/preferences; ключ
  пользовательского кэша содержит user ID и revision. После записи состояния
  новый GET обязан видеть изменение. Не кэшировать целиком чужие DTO.
- Ошибки провайдеров и `und` тоже кэшировать с retry policy, иначе каждый GET
  будет заново инициировать дорогую неуспешную работу.

### P2: polling и масштабирование

- Single-flight polling, следующий запрос после завершения предыдущего,
  backoff при ошибках, пауза скрытой вкладки; разделить статическую карточку
  и меняющиеся progress/download summaries.
- Наборы 15/150/1500 media и короткие/длинные сериалы, данные разных пользователей.
  Проверять число SQL и файловых операций, не только время на маленькой базе.
- Прогрев trickplay ограничить demand/квотой: не генерировать всё видео сразу.

## Подготовленная инструментальная база

Включение: `lazarr serve --log performance`, `LAZARR_LOG=performance` для
Docker или `RuntimeConfig(log="performance")`. По умолчанию `standard`.
В этой работе изменён только локальный код; Unraid этот logger ещё не получил.

Строка logger `uvicorn.error.performance` содержит `request_id`, HTTP method,
шаблон route, status, `duration_ms`, `ttfb_ms`, `completed`.
`duration_ms` измеряется до возврата ASGI-приложения, включая потоковую передачу
и cleanup/background response work; `ttfb_ms` — до отправки заголовков
(серверная метрика, не сетевой TTFB клиента). Незавершённый stream имеет
`completed=False`, даже если уже отправлен status 200. Без начала ответа при
исключении логируется 500. WebSocket-сессии не являются HTTP-запросами и не замеряются.
Заголовки `Server-Timing: app;dur=...` и `X-Request-ID` связывают Network и лог.
Необработанный 500 формируется внешним middleware, поэтому timing headers
для него не гарантированы. Query string, пароли и тело в performance log не попадают.
Обычный Uvicorn access log не изменён и может содержать query string: для
приватного тестирования использовать token header, не `api_key` в URL.

Повторяемый последовательный smoke benchmark (пароль запрашивается скрыто):

```sh
nix develop --command python scripts/benchmark_http.py http://127.0.0.1:8000 --repeat 5
nix develop --command python scripts/benchmark_http.py http://192.168.5.5:8003 "/Items/EPISODE_ID" "/Items/EPISODE_ID/PlaybackInfo" --repeat 5
```

Скрипт печатает JSONL samples, status, bytes, duration, request ID, median/max;
не сохраняет тела ответов, не очищает кэш, не запускает воспроизведение.
Авторизация создаёт тестовую сессию; обычные GET текущей реализации сами могут
выполнить enrichment/probe — это часть измеряемого поведения.

### Следующий контрольный прогон / критерии приёмки

- Записать commit/image, размер библиотеки, активные загрузки, версию плагинов,
  клиента и окружение; повторить те же IDs/фильтры до и после.
- Cold только на стенде: рестарт приложения отдельно от resource/file cache.
  Не сбрасывать Linux page cache и production кэш ради эксперимента.
- Warm: 20+ повторов для предварительного p95, дополнить более длинным прогоном;
  отдельно concurrency 1 и 3, лёгкий health probe для event-loop lag.
- Целевые бюджеты (предложения, не достигнутые результаты): warm main API
  p95 <500 мс, detail <250 мс, PlaybackInfo <250 мс, health <100 мс при чтении
  каталога. Streaming оценивать по старту, не по полной длительности фильма.
- Пустой NextUp без гидратации всей библиотеки; одиночный episode GET не делает
  файловые проверки чужих произведений. Ни один catalog GET не запускает ffmpeg
  или сетевое metadata enrichment; SQL tasks не растёт на два запроса на subtask.
- Тесты invalidation: замена файла, новые sidecar, удаление, смена языка,
  progress/favorite двух пользователей, restart, недоступный provider,
  stampede на холодном ресурсе. Проверить корректность DTO после оптимизации.
- Снять браузерный waterfall и render timings отдельно: HTTP logger не видит
  рендер, загрузку внешних постеров и задержки клиентского UI.

Первый этап изоляции реализован после составления плана: NextUp и detail WebUI
перенесены в наблюдаемый worker каталога; генерация thumbnails/trickplay,
субтитров/вложений, обработка изображений и probe — в worker медиа. Состояния
видны в попапе Tasks, готовые ресурсы читаются из кэша без ожидания media worker.
### Второй этап: уменьшение работы на чтении

Реализовано локально, ещё не опубликовано на Unraid:

- Playable-выборки ограничены произведением/эпизодом/asset. Карточка эпизода
  не строит версии других эпизодов; Jellyfin использует лёгкий read model без
  WebUI-представления файлов и дорожек.
- `list_tasks(media_id=...)` выбирает связи пакетно: максимум 7 SQL-запросов
  в regression-тесте вместо запросов на каждый subtask. WebUI карточка читает
  только свою задачу. CandidateDecision для detail также загружаются пакетно.
- NextUp предварительно отбирает сериалы с историей, рассчитывает кандидатов
  без MediaSources и формирует полные DTO только для выбранной страницы.
  Пустая история не вызывает detail. Явный SeriesId сохраняет прежнюю семантику.
- Items с явными Series/Movie, стандартным поиском/сортировкой сначала выбирает
  страницу. Запрос по IDs не строит ненужный общий каталог. Простая grouped
  Latest гидратирует только страницу; сложные фильтры сохраняют совместимый
  общий путь (их дальнейший перенос в SQL остаётся отдельной работой).
- Items/Latest/карточка Jellyfin выполняют DTO-сборку в worker каталога.
- Обычные GET библиотеки больше не вызывают provider enrichment или языковой
  ffmpeg. Фоновые циклы поддерживают метаданные и сохранённый в probe анализ
  неизвестных субтитров; `und` тоже сохраняется. Retry metadata 5 минут переживает
  рестарт. Кэш языка инвалидируется при изменении пути/size/mtime/stream/codec
  или версии алгоритма. Явное раскрытие ещё не загруженного сезона по-прежнему
  может запросить его метаданные: это не периодическое чтение каталога.
- Polling не накладывается; прогресс обновляется отдельно от полной карточки
  (3 и 30 секунд), смена состояния загрузки вызывает полное обновление.

Контрольный локальный HTTP smoke: одна и та же библиотека из 4 произведений,
3 последовательных запроса до и после перезапуска с новым кодом; медианы:

| Запрос | До, мс | После, мс |
| --- | ---: | ---: |
| Tasks | 21,11 | 12,57 |
| Карточка WebUI media 2 | 45,64 | 18,69 |
| NextUp Limit=12 | 68,25 | 26,69 |
| Items Series,Movie, Recursive, Limit=1 | 53,57 | 7,75 |

Это небольшой smoke, не p95, и не доказательство такого же ускорения Unraid:
фоновые задачи/нагрузка могли различаться. Production comparison нужно повторить
после разрешённого выпуска. Полная durable очередь, SQL-фильтрация сложных
каталожных запросов, события инвалидирования и профилирование остальных handlers
остаются следующими этапами.
