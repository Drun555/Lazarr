# Воспроизведение через Nginx Proxy Manager

> Архив: сведения о встроенном Jellyfin API относятся к версии до перехода на файловую медиатеку. Этот API удалён; клиенты подключаются к отдельному Jellyfin Server.

Lazarr отправляет `X-Accel-Buffering: no` для видеопотоков, включая remux
с внешней аудиодорожкой. Nginx учитывает этот заголовок, если он не отключён
через `proxy_ignore_headers`. Это предотвращает опережающее чтение большого
ответа во временные файлы прокси. Заголовок обычно не передаётся клиенту:
его отсутствие в ответе через nginx само по себе не означает ошибку.

При паузе плеер может перестать читать HTTP-ответ. Стандартный `send_timeout`
nginx составляет 60 секунд между записями клиенту. После закрытия соединения
плеер иногда продолжает проигрывать уже накопленный буфер и показывает ошибку
лишь при его исчерпании. Увеличение только `proxy_read_timeout` не решает этот
случай: он относится к чтению ответа от Lazarr, а не к отправке в плеер.

В Advanced нужного Proxy Host в Nginx Proxy Manager можно задать:

```nginx
send_timeout 3600s;
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
```

Проверить итоговый `nginx -T`: более конкретные настройки в `location`
имеют приоритет над настройками сервера. Если конфигурация игнорирует
`X-Accel-Buffering`, для обслуживающего видеопоток `location` дополнительно
задать `proxy_buffering off;`. После изменения проверить `nginx -t`
и перезагрузить конфигурацию штатным способом NPM. Таймаут остаётся конечным:
пауза больше часа может потребовать нового Range-запроса со стороны плеера.

Для диагностики сравнить тот же файл напрямую по IP и через прокси.
В error log искать `client timed out ... while sending to client` и
`upstream timed out ... while reading upstream`. Не публиковать строки
с `api_key` или другими токенами из URL.

Источники: [буферизация nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering),
[send_timeout](https://nginx.org/en/docs/http/ngx_http_core_module.html#send_timeout),
[proxy_read_timeout](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout).

## Локальная проверка 28 сентября 2026

Использован реальный `/Videos/{id}/stream` на Uvicorn и nginx:stable-alpine
(digest `sha256:0985e772fb9f729e6fa0980da05fca5d9c468e870eed43071545afa9d2e27d94`).
Клиент запросил Range на 64 МиБ, прочитал 64 КиБ, прекратил чтение на
75 секунд и затем продолжил. Размер приёмного TCP-буфера — 64 КиБ.

| Подключение | Получено | SHA-256 совпадает |
| --- | ---: | --- |
| Напрямую к Lazarr | 67 108 864 байта | Да |
| nginx с настройками по умолчанию | 4 304 896 байт, обрыв | Нет |
| nginx с send/proxy_read/proxy_send_timeout 600s | 67 108 864 байта | Да |

Это воспроизводит механизм обрыва на паузе, но не заменяет проверку
конфигурации и логов пользовательского NPM или самих Fladder/Infuse.
Продакшен в рамках проверки не изменялся.

Дополнительно регрессионные тесты вызывают настоящий Jellyfin-маршрут:
пауза с обратным давлением, возобновление, отключение и новый Range.
Подстановка прежнего FastAPI FileResponse приводит к двум ожидаемым
падениям: после отключения прочитаны все 8 МиБ тестового файла.
С обработчиком Lazarr чтение прекращается и файловый дескриптор закрывается.
