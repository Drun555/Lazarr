# Lazarr

Lazarr — лёгкий медиаменеджер на Python с WebUI, поиском произведений, задачами по фильмам и эпизодам, объяснимым сопоставлением раздач, проверкой медиа через ffprobe и встроенным libtorrent. Приложение использует FastAPI, SQLAlchemy/Alembic, серверные HTML-шаблоны и JavaScript без отдельного frontend-фреймворка. Подробности устройства и поведения находятся в `README.md` и `docs/`.

- GitHub: https://github.com/Drun555/Lazarr
- Docker Hub: https://hub.docker.com/r/drun555/lazarr
- Docker image: `drun555/lazarr`
- GitHub Actions workflow: https://github.com/Drun555/Lazarr/actions/workflows/docker.yml
- Локальный WebUI: http://127.0.0.1:8000

## Старт каждого чата

В начале каждого рабочего чата по Lazarr, до анализа и изменения кода, убедиться, что локальный сервер отвечает:

```bash
curl -fsS http://127.0.0.1:8000/health
```

Ожидаемый ответ — `{"ok":true}`. В тестовом режиме Lazarr и FlareSolverr запускать с bind-адресом `0.0.0.0`, чтобы они принимали подключения не только через loopback.

Если сервер не запущен, запустить его в сохраняющейся терминальной сессии и дождаться успешной проверки `/health`:

```bash
nix develop --command python -m lazarr.cli serve --host 0.0.0.0 --port 8000
```

Одновременно с Lazarr всегда должен работать локальный FlareSolverr. Проверить его готовность по адресу `http://127.0.0.1:8191/`; ожидается JSON с сообщением `FlareSolverr is ready!`. Если он не отвечает, запустить его в отдельной сохраняющейся терминальной сессии и дождаться готовности:

```bash
HOST=0.0.0.0 PORT=8191 LOG_LEVEL=warning LOG_HTML=false nix run .#flaresolverr
```

Сразу после запуска сервисов войти в Lazarr тестовым аккаунтом, получить список провайдеров и для каждого провайдера с полем `flaresolverr_url` сохранить значение `http://127.0.0.1:8191`, не меняя его включённость, остальные настройки и сохранённые секреты. Сейчас такое поле есть у Rutracker. После сохранения повторно прочитать настройки и убедиться, что URL применился.

Если Lazarr проверяется внутри локального Docker Compose, поднимать оба сервиса через профиль `cloudflare` и указывать провайдерам доступный из контейнера адрес `http://flaresolverr:8191`, а не loopback хоста:

```bash
docker compose --profile cloudflare up -d --build
```

Для локальной разработки использовать фиксированный тестовый аккаунт:

```text
URL:      http://127.0.0.1:8000
Логин:    lazarr-local
Пароль:   Lazarr-Local-9mQ4-vT7x
```

Это публичные локальные тестовые данные, а не секрет. Не использовать их в Unraid, Docker Hub, GitHub или любом другом внешнем/production-окружении. Если аккаунт отсутствует или вход не проходит, создать либо восстановить только аккаунт `lazarr-local` в локальной базе разработки; не удалять базу и не изменять другие аккаунты.

Не повторять в сообщениях URL, учётные данные и статус локальных сервисов, если они уже работали. Сообщить данные для подключения и статус только тогда, когда Lazarr был поднят в ходе текущей работы; о FlareSolverr сообщать только при его запуске или проблеме с запуском. Если сервис запустить не удалось или URL FlareSolverr не удалось записать в настройки провайдеров, сразу указать конкретную причину.

## Обычная разработка

По умолчанию разрабатывать и проверять изменения на локально поднятом сервере. Не пушить коммиты, не публиковать Docker-образ и не изменять контейнер в Unraid, если пользователь явно не написал «билдим» или «заливай».

1. Проверить состояние рабочей копии и не затрагивать несвязанные пользовательские изменения.
2. Использовать локальные Lazarr и FlareSolverr, проверенные и связанные через настройки провайдеров при старте чата:

   ```bash
   nix develop --command python -m lazarr.cli serve --host 0.0.0.0 --port 8000
   ```

3. После изменения серверного кода перезапускать процесс, если изменение не подхватилось. Для проверки контейнерно-специфичного поведения при необходимости использовать локальный `docker compose`, но не выполнять push образа.
4. Проверить изменённое поведение через локальный WebUI/API и выполнить релевантные тесты. Для полного прогона использовать:

   ```bash
   nix develop --command pytest -q
   nix develop --command ruff check src tests scripts
   nix develop --command ruff format --check src tests scripts
   npm run test:ui
   node --check src/lazarr/static/app.js
   ```

5. Сообщить локальный результат. Не считать обычные слова «готово», «исправь», «собери локально» или просьбу протестировать разрешением на публикацию.

## Публикация: «билдим» или «заливай»

Любая из этих фраз является явной командой выполнить весь процесс выпуска: commit → push → GitHub Actions → Docker Hub → Unraid. Не останавливаться после push или успешной сборки.

1. Просмотреть diff и включить в коммит только относящиеся к задаче изменения. Не захватывать посторонние изменения из грязной рабочей копии. Перед повторным запуском проверок учесть результаты непосредственно предшествующего шага: если после последних изменений уже были выполнены все релевантные проверки и они прошли, использовать эти результаты и не запускать те же проверки отдельно. Повторять проверки только если после них менялся код, набор проверок был недостаточен или изменилась среда выполнения.
2. Создать осмысленный коммит и отправить его в `origin/main`. Docker workflow запускается при push в `main`. Если изменения находятся не в `main`, не переписывать и не подменять историю: сначала привести ветку к принятому в репозитории способу попадания в `main`.
3. Получить полный SHA опубликованного коммита и вычислить Docker-тег как `sha-<первые 7 символов SHA>`. Workflow `.github/workflows/docker.yml` создаёт именно SHA-тег наряду с `latest`; для развёртывания всегда использовать SHA-тег, никогда `latest`.
4. Дождаться завершения GitHub Actions workflow `Docker image` именно для этого commit SHA. При ошибке изучить логи, исправить причину в рамках задачи, повторно проверить, закоммитить и отправить исправление; к Unraid переходить только после успешной сборки.
5. Проверить, что `drun555/lazarr:sha-<short-sha>` действительно доступен в Docker Hub. Одного зелёного статуса workflow недостаточно, если тег ещё не читается из registry.
6. Войти в WebUI Unraid, открыть редактирование контейнера Lazarr и заменить поле образа/Repository на:

   ```text
   drun555/lazarr:sha-<short-sha>
   ```

   Применить изменение, чтобы Unraid скачал образ и пересоздал контейнер. Сохранить существующие volumes, ports, variables и остальные настройки. Не менять репозиторный шаблон `unraid/lazarr.xml` на одноразовый SHA-тег, если пользователь отдельно этого не попросил.
7. Убедиться, что контейнер Lazarr запущен с ожидаемым SHA-тегом, WebUI открывается и базовая проверка изменённой функции проходит. При неуспешном старте изучить логи; не переключаться молча на `latest`.
8. В итоговом сообщении указать commit SHA, опубликованный Docker-тег, результат GitHub Actions и результат обновления/проверки Unraid.

Если адрес или учётные данные Unraid недоступны в текущей среде, завершить commit, push и проверку Docker Hub, затем явно сообщить единственный оставшийся блокер и запросить только недостающий доступ. Не просить пользователя вручную выполнить уже доступные агенту шаги.
